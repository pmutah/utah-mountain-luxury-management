| Ops | Email sign-in, the same shape as the Performance Motors DMS | sample | The dashboard is reached with a Google account whose address is on an allowlist, mirroring the DMS `staffAllowlist.ts`: a comma-separated list, normalised the same way, with a bootstrap default so a missing env var is not a lockout. The three addresses are `pmutah@gmail.com`, `stephlouw@gmail.com`, and `utahviper@hotmail.com`; setting `ALLOWED_EMAILS` **replaces** the built-in list, which is what "put the emails we want into the program" has to mean, and removing an address revokes it on the next request even if that browser still holds a valid cookie. **The proof differs from the DMS on purpose.** DMS uses Firebase ID tokens; this app is on Pages with Google Identity Services, so the credential is a Google ID token. Five things are checked before the allowlist means anything: the signature is Google's (verified against Google's published keys, not merely decoded), the **audience is this app's client id** (without it a token minted for any other Google app could be replayed), the issuer is Google, `email_verified` is true (an unverified address is just a claim), and the token has not expired. Every failure returns one message, so a caller cannot learn how close they are. The session cookie is **signed with an HMAC**, because the old cookie was base64 of the password — safe only because a password is secret, while an email is not: `btoa("attacker@evil.com")` would otherwise be a valid session. The HMAC covers the address and the issue time, so neither can be edited, and the signature is compared in constant time. `hostOnly` gained the email path in the one place all 68 host routes already pass through, so no route was edited; the password still works as a fallback, and a deployment with neither refuses everyone. `SESSION_SECRET` (16+ chars) and `GOOGLE_OAUTH_CLIENT_ID` are required; without the secret the email path is closed rather than open, and the session route reports the site as closed instead of claiming it is unprotected. **Setup state:** `SESSION_SECRET` (48 random characters, generated here) and `ALLOWED_EMAILS` are set in the Cloudflare **production** environment, and `GOOGLE_OAUTH_CLIENT_ID` was already there. Wrangler has no flag for the preview environment, so `elite-rebuild.wilhite-portfolio.pages.dev` still reports email sign-in as unconfigured — that has to be mirrored in the Cloudflare dashboard, or the branch merged to `main`. **`node:crypto` is not available on this runtime.** The first version used `createHmac` and passed every local test, then the deploy failed with `No such module node:crypto`: TypeScript knew the types because `node` is in `tsconfig.functions.json`, but the Workers runtime has no Node built-ins without `nodejs_compat`. Enabling that flag to fix one file would change module resolution for all 98 routes, so SHA-256 and HMAC-SHA256 are written out in `sha256.ts` and checked against Node's own implementation at the 55, 56, and 64-byte block boundaries, where a hand-written hash usually breaks. **Live on production since 2026-11-07.** `main` was fast-forwarded 128 commits, then merged with `origin/main` — which turned out to be an *older* line (September 23) carrying five files this branch lacked, including `muse/do.ts` and `amanda/do.ts`. Merging kept them; the route guard check then refused to deploy until those two bearer-gated bot routes were classified, which is the check doing its job. Verified on `wilhite-portfolio.pages.dev`: `/api/auth/login` reports `emailSignIn: true`, the real client id, and `3 email addresses have access`; a forged credential answers 401 `bad-token`; `/api/expenses`, `/api/reservations`, and `/api/portfolio/metrics` all answer **401 `sign-in`** rather than the old 503. The one thing still unverified from here is that the Google client's **authorized JavaScript origins** include the production and preview URLs — without that the button loads but Google refuses the redirect, and only the Google console can confirm it. **The password box promised something that did not exist.** `DASHBOARD_PASSWORD` was never set, yet the gate rendered the form unconditionally — so the live login screen showed a password field on a deployment with no password, and typing into it failed with nothing explaining why. The gate now asks the server which sign-in methods exist and renders only those, an error from a Google attempt has somewhere to appear when there is no password form, and a deployment with neither method says so. A test fails if the form is ever unguarded again; it was checked by unguarding it. **`origin_mismatch` on first real sign-in:** Google rejected the button because the deployment's origin is not registered against the OAuth client. That is a Google Cloud Console change, not code — Authorized JavaScript origins needs `https://wilhite-portfolio.pages.dev` and `https://elite-rebuild.wilhite-portfolio.pages.dev` — so a `DASHBOARD_PASSWORD` was set as a working way in meanwhile. |

| Data safety | A failed read can never overwrite the books | live | `kvGet` used to catch **every** read failure and return the caller's default, so a network blip, a rate limit, and a value that would not parse all looked exactly like "this key was never written". `createReservation` read `[]`, appended the stay it had just built, and saved that one row over `reservations`; the only guard was on a *completely* empty list, so a one-row list passed it. One create on a flaky connection replaced every saved booking, and `saveSession` had the same shape. A failed read is now a `StorageReadError` and only `raw === null` (never written) yields the default, which is the truth. `kvPut` compares against what is actually saved — reusing the read the route already made, so the guard costs no extra KV read — and refuses any write that would leave **fewer** rows on `reservations` or `customExpenses` than it found; turnover `clean-` rows are exempt because they are derived from stays. Editing an expense (same length) and adding one (longer) both still save. `ledgerSafeToSave` also had its empty case backwards: it refused the first write, so on a fresh ledger the turnover cleaning rows were silently never created and the caller reported `0` as though there were nothing to do. A first write is allowed now, and a refusal throws instead of returning `0`, because a refusal that reads as success is how a missing expense row goes unnoticed. Eleven tests drive the real stores against a KV that blips, hits a limit, and returns truncated JSON, and four of them fail on the old code. The guard first shipped covering only bookings: `saveCustomExpenses` wrote to KV directly instead of going through `kvPut`, so the expense ledger — the larger of the two — was never checked, while the registry said it was. It delegates now, and a test pins the coverage rather than the mechanism so re-inlining the write fails. A deliberate delete still works: removing an archived expense is a legitimate shrink, so `kvPut` takes an `allowShrinkReason` and the delete route names the archive it already made, which keeps the one intended removal possible without reopening the shape every accidental wipe has. A stay that cannot be used is no longer saved.
